# AxiomGuard 0.6.0

AxiomGuard 0.6.0 expands the SDK from reusable security primitives into a more complete request-protection layer while preserving the zero-runtime-dependency core.

## Highlights

### Browser request policy

The new `@axiomnode-lab/guard/request-policy` module evaluates unsafe browser requests using Fetch Metadata and strict Origin fallback. `cross-site` unsafe requests, `Origin: null`, unknown metadata and missing-origin requests are rejected by default. `same-site` remains conservative unless explicitly trusted.

Express, Fastify and Hono adapters can opt into the policy without changing existing applications that do not configure `requestPolicy`.

### Idempotency claims

The new `@axiomnode-lab/guard/idempotency` module provides:

- bounded in-memory claim state
- normalized and hashed client keys
- length-delimited request fingerprints
- `accepted`, `replay`, `conflict`, and `capacity` outcomes
- node-redis and ioredis atomic Lua-backed stores

The feature intentionally does not pretend that an in-memory/request-fingerprint claim is a complete idempotent transaction system. Durable response replay and database transaction semantics remain application responsibilities.

### More provider-aware webhook verification

`/webhooks` now includes:

- Meta/WhatsApp `X-Hub-Signature-256` verification against raw request bytes
- Slack v0 signed-request verification with timestamp freshness and optional replay state
- canonical Stripe and Slack replay identities that cannot be bypassed by harmless signature/header representation changes

Existing GitHub, Stripe and generic HMAC helpers remain available.

### Packaging and qualification

The package tarball now ships the complete `docs` directory so README links resolve for installed consumers. Clean-room qualification imports the new subpaths and checks their TypeScript declarations. Real framework tests exercise request-policy blocks, while Redis integration tests validate distributed idempotency claims and TTL behavior.

## Compatibility

- Node.js: `>=20`
- package type: ESM
- runtime npm dependencies: none
- existing exported modules remain available
- request-policy enforcement in framework adapters is opt-in

## Security boundaries

- Request policy is not authentication or authorization.
- CORS does not replace CSRF/request-origin policy.
- Idempotency claim state does not store the application response or make database work transactional.
- In-memory replay/idempotency/rate-limit stores are single-process; distributed deployments should use shared stores.
- Meta/WhatsApp signature verification requires the exact raw body and does not provide a universal provider event-deduplication ID.
- `safeFetch` remains subject to the documented DNS validation-to-connection TOCTOU boundary.

See `THREAT_MODEL.md` and `docs/API_PROTECTION.md` before enabling these controls in a production service.
